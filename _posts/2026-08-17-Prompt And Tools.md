如何拥有一个简单的思维模型去理解和思考agent的概念？实际上并不难，从一个简单的聊天开始，这个思维模型很快就可以构建起来。

## A Prompt
Prompt的作用是提供意图和标准，是推理的开始。
**你**
> 分析一下今天的天气对股票大盘走势的影响

**LLM**
> 我无法获取外部数据，需要你提供今天的天气信息以及股票大盘的数据，然后我会为你提供分析报告

好的接下来你往窗外看了一下，今天是晴天。然后打开了你经常浏览的股票网站，复制粘贴了一大段数据，然后...
**你**
> XXXX 这么麻烦？？？？？

**LLM**
> 卧槽，用户彻底怒了。

一些token被浪费了，但是毫无进展。你开始想到底怎么能够让LLM做到这件事情，在你拿到分析报告之前可以多刷会短视频。你刷着短视频，你突然想到了一个解决这个问题的方案，你觉得自己是个天才，然后继续刷着短视频，刷到困得不行才肯睡着。
第二天到了。
从输入和输出上来看，大语言模型本质上是不断根据当前token序列不断给出下一个token的分布，文本进文本出。API的文档是文本，它想传的参数页可以作为文本传递，API的结果也可以作为文本传递。我要做的事就是，从文本中解析参数，调用API，然后将结果作为文本发回给大模型，这个事可以通过程序自动做到。这样我就再也不需要复制粘贴了。
于是你开始对话，探讨idea。

**你**
> 给我分析下面这个方案可行性，我会给你一些方法定义和schema，主要用来提供搜索和访问网页的功能。当你需要搜索或者访问网页的时候，你通过一个json告诉我你要怎么调用。然后我会使用一个循环，当接收到你的json时候，这个循环会根据json调用指定的方法，获取输出结果后返回给你。这样你就可以自己决定如何获取资料了，你觉得这个方案可行吗

**LLM**
> 思考评估网页访问方案的可行性和实现逻辑
> 搜索现在有的方案
> ....
> 可行,而且这正是目前主流 Agent 框架(ReAct / tool calling)的标准做法,不是什么新奇路子

**你**
> ？？？？

**LLM**
> 卧槽，用户 Out of date 了。

## Tools
Tool是模型和外界环境交互的协议，模型会告诉Agent如何调用Tool，然后Agent会将执行结果作为message发回给模型。
Tool给予了agent无限可能，数据获取，写文件，访问网页，调用其他程序，控制你的电脑，但这不说明tool越多越好、越全越好，如何设计一套良好定义的工具箱依然是一门哲学。
> 简单来说，tool的价值 = 能力价值 + 治理价值 - 决策成本 - 上下文成本。
有几个思考的方向
1. tool越多，越少可用的上下文，因为tool本身会作为system prompt的一部分占用上下文。
2. tool越多，越难保证正交，因此不得不引入编排说明解决冲突，可用的上下文又变少了。
3. tool的能力价值高，不代表它的成本就高，这就叫杠杆。

### Tool的上下文成本
Tool的上下文成本由Tool Schema和在System Prompt指导模型对该Tool的使用有关。例如openAI的API协议request一般是
```json
{
    "systemPrompt": "",
    "messages": [..],
    "tools": [...]
}
```
下面可以对比两个Harness，一个是功能完备的codex，另一个是极简设计的pi agent。
Evaluation的过程是，使用codex和pi在同一个项目分别发送一个hello消息。然后分析他们的上下文使用情况。
> 注意tools的占用情况是推算出来的，因为从API来看，它们是单独的参数，不以message的形式出现。方法是token usage - token usage of messages.

| 分类 | Codex Tokens | Codex 占比 | Pi Tokens | Pi 占比 | 占比差异（Pi - Codex） |
| --- | ---: | ---: | ---: | ---: | ---: |
| System Prompt | 8,003 | 32.72% | 2,606 | 79.23% | +46.51p |
| Tool schema  | 13,560 | 55.44% | 682 | 20.74% | -34.70p |
| User Prompt | 2,897 | 11.84% | 1 | 0.030% | -11.81p |

可以看到Codex由于Tools比较多，占用了约14k的toekn是pi的快20倍，算是非常直观的体现了。
### Tool的决策成本
Tool的决策成本取决于它的正交做得有多好，即Tool之间的能力的交集的大小。以pi agent举例，它的基础的tools有read、edit、write和bash。read是读取一个文件内容，write是覆盖和创建某个文件，edit是精确编辑文件的某一部分，bash则是执行任何命令。其中bash几乎可以做到任何事情，write和edit可以相互替代。
每个工具都有它适合的场景但同时它们又相互冲突，解决的方式是编排，在system prompt里列出什么场景应该使用什么命令，指定优先级。
但是有时候优先级是不好指定的，例如write和edit，edit需要定位需要替换的文本并使用新的文本替换它，但要替换的文本过长时，不如直接write。
但是多长算长呢，这是不太容易决定的问题，也不应该明确，想象下指定替换文本>30%文件长度的时候使用write这个prompt，要做到它，大模型可能会通过bash去计算对应长度得到精确的数值，或者花更多的token思考要不要替换以达到标准。
### Tool的治理价值
很多情况下bash能做到各种各样的事情，为什么不使用bash去读去编辑呢？主要是治理价值低，有很多原因，第一个是编辑脚本不稳定而且编辑脚本包含了code和schema，code占用了多于上下文窗口。第二个是审计需要，对于修改操作，我们总会希望可以可视化方便用户审阅变更，或者定义一些规则，例如一个文件能够被edit tool处理，必须是先被read tool读过，保证上下文里真的有这个文件内容，减少出错可能性。
### Tool的能力价值
高杆杠tool具备上下文成本极低和决策成本极低的特点，使用方式和场景已经内化在大模型里了。这个意思是说大模型天生就擅长某些东西，tool应该充分贴合大模型的能力分布，否则需要更多的prompt来保证tool被正确的使用。一个假设是coding/sh脚本这些训练数据质量高数量大，并且很容易被RL训练，提供一个通用的bash tool很多时候就可以解放agent很多能力，并且同时拥有极高的正确率。
不过需要注意的是，在windows环境，则没有这么多高质量的数据，总是能听到一些来自windows的大新闻，例如删除所有文件。所以这里会有种悲观的观点，大模型会让你变得平庸，因为旧的、被多人使用的知识、工具才会更多的被训练，然后他们又被大模型加强从而占有更具生态的地位。
